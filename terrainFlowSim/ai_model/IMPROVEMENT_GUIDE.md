# 모델 검증 · 성능 개선 가이드

작성 2026-09-15. 대상: `checkpoints_v5/best.pt` (FiLM rain+time + GAN, 256px, in_ch=3, cond_dim=2).

이 문서는 "무엇을 개선할까"가 아니라 **"개선했다고 말할 자격을 어떻게 얻을까"** 의 순서를 정한다.
지금까지의 실험(EXPERIMENTS.md)에서 가장 비싼 실수는 *측정이 잘못된 상태로 아키텍처를 바꾼 것*이었다.
v1~v4가 val L1 0.068에서 멈춘 원인은 모델이 아니라 타깃 렌더링 버그였고, 그걸 모른 채
채널결합 / FiLM / GAN 세 가지를 차례로 시도했다. 같은 실수를 반복하지 않기 위한 원칙:

> **측정 → 판정 → 변경.** 어떤 변경도 그것을 검증할 지표가 먼저 존재할 때만 시작한다.

## Phase 0 — 재현 가능한 평가 기준선 (선행 필수)

**문제**: `deploy_package/README.md`에 적힌 성능 수치(MAE 0.0049m, r=0.919, 강우 단조성 70/70)는
애드혹으로 계산된 값이고, 같은 숫자를 다시 뽑는 스크립트가 저장소에 없다. 재현 불가능한 숫자는
보고서에도 못 쓰고, 개선 여부 판정의 기준도 될 수 없다.

**할 일**: `scripts/evaluate.py` — 체크포인트 하나를 받아 val 전체를 평가하고 표/CSV/그림을 낸다.

측정 대상은 **배포되는 경로 그대로**여야 한다. 즉 `등고선 PNG → UNet → 예측 RGB → Blues 역LUT →
norm_to_depth → 수심[m]`. 모델 출력 텐서를 직접 쓰면 실제 사용자가 받는 값과 다른 것을 재게 된다.

정답은 학습 타깃 PNG가 아니라 **OpenFOAM 원본 `depth.npy` / `depth_series.npy`(96×96, 단위 m)** 를 쓴다.
PNG 타깃과 비교하면 렌더링 손실이 정답 쪽에도 똑같이 들어가서 오차가 실제보다 작게 나온다.

지표 (픽셀 L1만으로는 이 과제의 실패 모드가 안 잡힌다):

| 지표 | 왜 |
|---|---|
| MAE / RMSE [m] | 기본 크기 오차 |
| Pearson r | 공간 패턴 일치 |
| **젖은영역 IoU @1cm / @5cm** | "어디가 잠기나"의 실제 정답률. 배수구 위치 판단의 근거 |
| **최심점 위치 오차 [m]** | 가장 위험한 지점을 맞추는가 |
| 타깃공간 L1 | 학습 로그(val L1)와의 연결 고리 |
| **강우 단조성** | 같은 지형·같은 시점에서 비가 많을 때 더 깊게 예측하는 비율. v5의 핵심 주장 |
| **D4 등변성 오차** | 같은 지형의 회전본 8장 예측이 서로 얼마나 다른가 = 모델이 지형이 아닌 렌더링 인공물에 반응하는 정도 |

분해 보고: **지역별(seoul/busan/gangwon) · 강우량 구간별 · 시점(t0~t5)별**.
평균 하나로는 gangwon 79종의 취약함이 busan 284종에 가려진다.

**게이트**: README의 주장(MAE ≈ 0.005m, r ≈ 0.92, 단조성 100%)이 재현되지 않으면
Phase 1로 넘어가지 말고 원인부터 찾는다.

### Phase 0 결과 (2026-09-15, `eval_v5/summary.md`)

`scripts/evaluate.py` 로 val 87지형·911장 평가. **README 수치는 재현되지 않았다.**

| 지표 | README 주장 | 재현값 | |
|---|---:|---:|---|
| MAE | 0.0049 m | **0.0110 m** | 2.2배 |
| 상관계수 r | 0.919 | **0.684** | |
| 강우 단조성 | 100% (70쌍) | **98.8%** (403쌍) | 사실상 재현 (GT 상한 99.3%) |

README 수치는 아마 OpenFOAM 원본이 아니라 타깃 PNG와 비교했거나 표본이 작았던 것으로 보인다.
**보고서에는 `eval_v5/summary.md` 값을 쓸 것.**

새로 드러난 사실 4가지:

1. **`predict_depth_*` 반환 배열이 입력 지형 대비 상하반전이다.** 보정 전후 상관계수
   0.17 → 0.79. 렌더링이 `contourf`(Y 위로 증가)와 `imshow(origin="lower")`를 거치면서
   생기는 문제로, 입력·타깃이 같이 뒤집혀 학습엔 지장이 없지만 API 사용자는 틀린 지도를 받는다.
   `evaluate.py: to_array_orientation()` 참조. → Phase 3에서 수정.
2. **최대 수심을 절반으로 예측한다** (비율 중앙값 0.509, 편향이 음수인 샘플 82%).
   평균 수심 비율은 0.811이니 전체가 작은 게 아니라 **피크만 무너진다.**
3. **표현 방식 탓이 아니다.** `scripts/diagnose_pipeline.py` — 정답을 모델 없이 같은
   파이프라인(sqrt 정규화 → Blues 8bit RGB → 역LUT → 리사이즈)에 통과시키면 최대수심
   비율 **0.928**, MAE 0.0003 m. 즉 천장은 0.93인데 모델은 0.49다.
4. **지역 편차가 크다.** gangwon(79지형) r=0.30 / IoU@1cm=0.30 vs busan(284지형) r=0.76 / 0.78.

### Phase 0-B — 데이터냐 목적함수냐 (train vs val 대조)

같은 지표를 **학습에 쓴 지형**에서도 재서 두 원인을 분리했다
(`--split train`, `eval_v5_train/`).

train 표본은 val 과 지역 구성이 같아야 한다. `--limit-terrains` 가 처음엔 알파벳 순으로
잘라서 busan 만 뽑히는 바람에 격차가 과장됐었다(r -0.14). seed 고정 무작위 추출로 고친 뒤:

| 지표 | train | val | 격차 | 해석 |
|---|---:|---:|---:|---|
| **최대수심 비율** | **0.530** | **0.509** | **-0.02** | **격차 없음 → 데이터로 못 고침** |
| 상관계수 r | 0.761 | 0.684 | -0.077 | 일반화 격차 |
| IoU@1cm | 0.733 | 0.679 | -0.054 | 일반화 격차 |
| IoU@5cm | 0.452 | 0.378 | -0.074 | 일반화 격차 |
| 최심점 오차 | 292 m | 324 m | +32 | 일반화 격차 |

지역별 r 도 같이 보면: busan 0.852→0.761, seoul 0.717→0.642, **gangwon 0.288→0.301**.
**강원은 학습 지형에서조차 못 맞춘다** (일반화 실패가 아님). GT 평균 수심이 0.0051m로
busan(0.0316m)의 1/6이라, 아주 얕은 물을 현재 타깃 표현이 담지 못하는 쪽에 가깝다.
→ **강원 지형을 더 모으는 것으로는 안 풀릴 가능성이 크다.**

**결론: 섞여 있던 두 문제를 분리했다.**

- **문제 A — 피크 평탄화(2배 과소예측).** 학습에 쓴 지형에서도 동일하게 나타난다.
  일반화 실패가 아니라 **목적함수 문제**다. 지형을 아무리 늘려도 안 고쳐진다.
  L1이 얇은 배수채널(전체 픽셀의 소수)을 뭉개는 쪽을 선호하기 때문.
- **문제 B — 공간 패턴 일반화.** r·IoU에 뚜렷한 train/val 격차가 있다. 여기는 데이터가 듣는다.

따라서 **Phase 2의 목적함수 수정(A)이 Phase 1의 데이터 확보(B)보다 먼저다.**
A는 GPU 몇 시간, B는 OpenFOAM 며칠인데 지금 지배적인 오차는 A다.

## Phase 1 — 데이터가 정말 병목인지 판정 (스케일링 곡선) · **문제 B 전용**

> Phase 0-B 결과로 이 단계의 역할이 좁아졌다. 스케일링 곡선은 **문제 B(r·IoU 일반화 격차)**
> 에만 답하는 실험이다. 문제 A(피크 평탄화)는 여기서 답이 나오지 않으므로 Phase 2를 먼저 한다.

**문제**: "지형 수가 병목"은 EXPERIMENTS.md의 가설이지 검증된 결론이 아니다. 근거가 약한 이유:

| | 8월 말 | 현재 | 배율 |
|---|---:|---:|---:|
| 학습 쌍 | 4,568 | 48,528 | 10.6× |
| **고유 지형** | 491 | **586** | **1.19×** |

10배 늘어난 것은 시점(6×)과 D4 증강(8×)이지 지형이 아니다. 즉 "데이터를 늘려도 배수채널이
흐릿하다"는 관찰은 **지형 다양성 가설을 반증하지도 지지하지도 않는다.**
현재 지역별 고유 지형: busan 284 / seoul 223 / gangwon 79. 원본 시뮬 1,086개(지형당 평균 1.7 강우조건).

**할 일**: `scripts/scaling_study.py` — 학습에 쓰는 **지형 그룹 수**만 바꿔가며 같은 설정으로 학습하고
Phase 0의 지표를 같은 val 셋(고정)으로 잰다.

- 지형 수: 대략 75 / 150 / 300 / 497(=전체 train)
- val 셋은 **네 조건 모두 동일**해야 한다. 지형 그룹 기준 split을 먼저 하고, train 쪽에서만 부분집합을 뽑는다.
- 비용을 감당하려면 축소 설정으로 돈다: 128px / ngf32 / epoch 상한 고정 / GAN 없음(unet).
  절대 성능이 아니라 **곡선의 기울기**를 보는 실험이므로 축소해도 결론은 유효하다.
  단, 네 지점이 **모두 같은 축소 설정**이어야 한다.

**판정**:
- 마지막 구간(300→497)에서 아직 뚜렷하게 개선 → 데이터가 병목. OpenFOAM 추가 투자 정당함.
  이때 외삽으로 "지형 몇 개가 더 필요한지"까지 추정해서 비용(샷당 10~20분)과 비교한다.
- 곡선이 평평 → **데이터 추가는 낭비**. Phase 2로 간다.
- gangwon만 곡선이 살아있다면 → 전체가 아니라 강원 지형만 추가 (가장 싼 답).

### 앞선 Phase 0-B 판단 정정

Phase 0-B에서 "피크 평탄화는 데이터로 못 고친다"고 썼는데, **너무 강한 표현이었다.**
스케일링 곡선에서 최대수심 비율은 지형 수와 함께 올라간다 (0.465 → 0.619, 지형 6.6배).
정확한 진술은:

- train/val 격차가 0.02로 작다 = 피크 평탄화는 **순수한 일반화 실패가 아니다** (이건 유효)
- 그래도 데이터를 늘리면 피크 비율도 같이 오른다 (2배당 +0.053)
- **둘 다 듣지만 비용이 다르다**: 목적함수 +0.127/21분 vs 데이터 +0.154/(지형 6.6배)

## Phase 2 — 목적함수 수정 (**문제 A**, 최우선)

**1. 젖은 픽셀 가중 L1** — 스칼라 브랜치에는 이미 있는데(`wet_weight=8`, EXPERIMENTS.md B1)
   이미지 브랜치에는 없다. 타깃이 젖어 있는 픽셀의 L1 가중치를 올려서, 소수 픽셀인 배수채널을
   뭉개면 손해가 되게 만든다. Blues 컬러맵에서 R채널이 흰색 0.97 → 진파랑 0.03으로 단조
   감소하므로 `wetness = 1 - R` 을 가중치로 쓰면 된다.

   **반드시 같은 축소 설정의 baseline과 쌍으로 학습한다.** v5(256px/GAN/55epoch)와 비교하면
   무엇 때문에 달라졌는지 알 수 없다.

### Phase 2 결과 (2026-09-15) — 가설 확인됨

축소 설정(128px/ngf32/unet)에서 `wet_weight` 하나만 바꾼 A/B. 비교는 `scripts/compare_evals.py`.

| 지표 | p2_base (w=1) | **p2_wet8** | 참고: v5 (256px/GAN/54.5M) |
|---|---:|---:|---:|
| **최대수심 비율** | 0.492 | **0.619** | 0.509 |
| 편향 [m] | -0.00371 | **-0.00128** | -0.00522 |
| IoU@5cm | 0.4031 | **0.4255** | 0.3778 |
| IoU@1cm | 0.6784 | **0.6884** | 0.6785 |
| 최심점오차 [m] | 307.8 | **299.5** | 323.7 |
| MAE [m] | 0.0112 | 0.0115 | 0.0110 |
| r | 0.6802 | 0.6817 | 0.6841 |

- **겨냥한 지표가 움직였다**: 피크 비율 0.49 -> 0.62 (천장 0.93). 과소예측 편향은 1/3로.
- MAE 소폭 악화는 예상된 트레이드오프(피크를 살리면 균등 L1은 손해). 대신 IoU·최심점오차가
  좋아졌으므로 실제 목적(어디가 얼마나 잠기나)에서는 순이득.
- 육안으로도 v5에서 균일한 안개였던 최악 사례가 수지상 배수망 구조로 살아남 (`eval_p2_wet8/worst_6.png`).

**부수 발견 — v5의 크기·GAN·256px는 값을 못 하고 있다.** 21분 학습한 128px/ngf32/GAN없는
10.5M 모델(p2_base)이 10시간 학습한 686MB v5와 모든 지표에서 동급이거나 낫다
(IoU@5cm 0.403 vs 0.378, 최심점오차 308 vs 324m). 배포 모델을 경량본으로 바꾸면
품질 손실 없이 체크포인트가 1/5로 줄어든다.

### 가중치 스윕 (wet8 / wet16 / wet32, 45 epoch) — **w=8에서 포화**

| wet_weight | 1 | **8** | 16 | 32 |
|---|---:|---:|---:|---:|
| 최대수심 비율 | 0.492 | **0.619** | 0.609 | 0.595 |
| IoU@5cm | 0.4031 | **0.4255** | 0.4198 | 0.4178 |
| IoU@1cm | 0.6784 | **0.6884** | 0.6824 | 0.6826 |
| r | 0.6802 | 0.6817 | 0.6822 | 0.6767 |
| MAE [m] | 0.0112 | 0.0115 | 0.0115 | 0.0117 |

w를 8 이상 올리면 오히려 나빠진다. **wet_weight=8 확정** (스칼라 브랜치가 예전에 찾은
값과 같다 - EXPERIMENTS.md B1).

## Phase 3 — 배포 반영 ✅ 완료 (2026-09-16)

배포 모델은 v5가 아니라 **`checkpoints_p2_wet8/best.pt`** 로 결정했다. Phase 2에서
128px/10.5M/GAN없는 모델이 686MB v5를 모든 물리 지표에서 앞선다는 게 확인됐기 때문.

적용한 것:

- `webapp/backend/app.py`: 기본 체크포인트 `checkpoints_film` -> `checkpoints_p2_wet8`.
  `/api/predict` 에 `time_s` 폼 필드 추가, 체크포인트가 요구하는 조건만 넘기도록
  `cond_dim` 기반 분기(0/1/2 모두 지원 - 구버전으로 되돌려도 뜬다).
  `/api/health` 에 `time_conditioned`, `time_range_s`, `default_time_s`, `image_size` 추가.
- `src/inference_api.py`: **학습 해상도 자동 판별**(`_infer_image_size`). 체크포인트마다
  해상도가 달라서(v5=256, p2_wet8=128) 고정값이면 모델을 바꿀 때마다 환경변수를 같이
  고쳐야 했다. state_dict 의 `submodule` 중첩 수 + 1 = log2(image_size)
  (체크포인트 4개로 검증). `AI_MODEL_IMAGE_SIZE` 를 주면 그 값이 우선한다.
- `webapp/frontend/index.html`: 경과 시간 슬라이더(0~120초) + **시점 애니메이션**
  (0~120초를 20초 간격 7프레임으로 미리 받아 재생/스크럽). 시점을 모르는 체크포인트가
  올라오면 슬라이더가 자동으로 숨는다.

**기본 조회 시점을 120초가 아니라 18초로 바꿨다.** 학습 데이터는 비가 초반에 내리고
이후 빠지는 시뮬레이션이라 수심이 시간에 따라 감소한다(val 정답 평균 t0 0.039m ->
t5 0.019m). `deploy_package/README.md` 가 권하던 `time_s=120` 은 가장 덜 잠긴 상태를
보여주는 값이라 해당 문서에 정정을 달았다.

검증 (포트 8011 임시 구동):
- `/api/health` -> `cond_dim=2`, `image_size=128`, `device=cuda`
- `/api/predict` terrain 모드, rain 70mm: 유출강도 t=0s **50.1** -> 60s 16.6 -> 120s 7.3
- 브라우저에서 샘플 클릭 -> 예측 -> 애니메이션 7프레임 생성까지 실제 동작 확인.
  프레임별 유출강도 41.7 -> 31.0 으로 단조 감소(물이 빠지는 과정이 실제로 보인다).

**남은 항목**: `best.pt` 는 옵티마이저·판별자를 같이 담고 있다(v5 686MB, wet8 125MB).
추론용 netG만 추출하면 wet8 기준 ~40MB. 제출물 크기가 중요하면 추출 스크립트를 추가할 것.

## Phase 4 — 데이터 누출 검증과 검증 탭 (2026-09-16)

### 웹앱 데모는 대부분 학습 지형을 보여주고 있었다

`/api/samples` 는 `data/contours` 에서 고르는데, 이 폴더에는 학습에 쓴 지형과 안 쓴 지형이
섞여 있고 구분이 없었다. 갤러리 30개 중 **25개(83%)가 학습에 쓰인 지형**이다.

배포 모델(p2_wet8) 기준 부풀림 정도:

| 지표 | train (누출) | val (정직) | 부풀림 |
|---|---:|---:|---|
| MAE [m] | 0.0069 | 0.0115 | 실제 오차가 **1.7배** |
| 상관계수 r | 0.835 | 0.682 | +0.153 |
| IoU@1cm | 0.787 | 0.688 | +0.099 |
| IoU@5cm | 0.581 | 0.426 | **+36%** |
| 최심점오차 [m] | 241 | 300 | |

참고로 이 격차(r +0.153)는 v5의 격차(+0.077)보다 크다. wet8 이 같은 데이터에서 더
오래/작은 해상도로 학습해 과적합이 좀 더 있다는 뜻이다. 그래도 val 절대 성능은 wet8 이 낫다.

### 겸사겸사 잡은 버그 — 지형 중복 집계

`app.py:_base_terrain_id` 가 `_(r|f)[0-3]$` 로 증강 접미사를 떼는데, 파일명에 `_t{idx}` 가
붙은 뒤로 **정규식이 전혀 매칭되지 않았다.** 그래서 같은 지형의 8개 회전본이 서로 다른
지형으로 집계돼 샘플 갤러리에 같은 지형이 여러 번 떴다. 학습 때 쓰는 `_group_key` 를
공유하도록 교체했다 (`src/ground_truth.py: group_key`).

### 검증 탭

`webapp` 에 **검증 탭**을 추가했다. 예측을 OpenFOAM 정답과 나란히 놓고 수치까지 낸다.

- `src/ground_truth.py` — 파일명 -> OpenFOAM 정답 조회, split 판정, 지표 계산.
  웹앱과 `scripts/evaluate.py` 가 "정답"을 다르게 구하는 사고를 막으려고 분리했다.
- `GET /api/testset?split=val|train&limit=N&min_depth_m=0.05` — 케이스 목록.
  **정답에 물이 거의 없는 케이스(강원 val 은 대부분 최대수심 1cm 미만)는 배수 예측 검증에
  정보가 없어서 뒤로 미룬다.** 몇 개가 밀렸는지 응답과 화면에 밝힌다 (조용히 고르면 체리피킹).
- `GET /api/testcase?name=...` — 그 샘플의 **실제 시뮬레이션 조건**(강우·시점)으로 예측하고
  등고선 / 정답 / 예측 3장 + MAE·r·IoU·최대수심비·최심점거리를 반환.
- 프런트: 케이스마다 `학습에 씀` / `학습 안 씀` 배지. 최대수심 비율은 평균이 아니라
  **중앙값**(마른 케이스에서 0 나누기로 폭발 - 실제로 평균 2.77 이 나왔다).

화면에서 바로 확인되는 대비 (같은 6케이스 설정):

## Phase 5 — 실행 환경 버그 (2026-09-16)

"첫 이미지 말고 다른 이미지는 예측 실패"를 추적하다 실행 환경 쪽 버그 3개를 잡았다.
예측 파이프라인 자체는 문제가 없었다(샘플 30개·업로드·두 모드·경계조건 전부 통과).

### 1. `run_windows.bat` 이 아예 실행되지 않았다

파일이 **LF 줄바꿈 + UTF-8(BOM 없음)** 이었다. cmd.exe 는 배치 파일을 CRLF 로 읽고
콘솔 코드페이지(한국어 Windows = CP949)로 디코딩하므로, 줄이 잘못 잘리고 한글이
깨져서 `'""'은(는) 내부 또는 외부 명령...` 같은 오류만 쏟아진다.
-> **CRLF + CP949 로 다시 저장** (원본은 `.bak`). `team_yucheital_backend-main/run_windows.bat`
도 같은 문제라 같이 고쳤다.

### 2. MariaDB 기동 경쟁

bat 이 `service mariadb start` 직후 바로 uvicorn 을 띄워서, DB 가 늦으면 `init_db()` 가
실패한다. 응답할 때까지 최대 20초 기다리는 루프를 넣었다.

### 3. DB 가 끊기면 예측이 전부 401 로 죽는다 ← **사용자가 본 "예측 실패"의 원인**

이 환경의 MariaDB 는 WSL2 안에 있고 Windows -> `127.0.0.1:3306` 포워딩이 수시로 끊긴다
(같은 분 안에 접속 20/20 성공 -> 20/20 실패를 관측).

`_DB_READY` 는 **기동 시점 한 번만** 판정된다. 기동 때 DB 가 살아 있으면 인증이 켜진 채
고정되는데, 그 뒤 포워딩이 끊기면 로그인·회원가입이 둘 다 DB 를 타므로 **토큰을 받을
방법이 없다** -> 모든 예측이 401 -> 프런트는 "예측 실패: 세션이 만료되었습니다".
`require_user` 는 HMAC 토큰만 검증하므로, 이미 토큰이 있으면 계속 되고 없으면 전부 막히는
들쭉날쭉한 증상이 된다.

설계 의도가 "DB 없으면 인증 생략" 이므로 그 의도를 **요청 시점에** 적용하도록 고쳤다:
- `app.py: _auth_gate` — 토큰 검증 실패 시 DB 가 실제로 죽었는지 확인해서, 죽었으면 통과.
  DB 조회는 실패 경로에서만 하므로 정상 예측 성능에는 영향 없음.
- `index.html: initAuth` — `auth_enabled && db != "ok"` 면 로그인 화면으로 막지 않고
  앱을 열고 상태줄에 `DB 끊김 — 로그인 생략` 배지를 띄운다.

검증: `auth_enabled:true` + `db:down` 상태에서 토큰 없이 6장 연속 200,
브라우저에서 예측 3장 + 검증 탭 4케이스 정상 (포트 8000, 실제 `run_windows.bat` 기동).
